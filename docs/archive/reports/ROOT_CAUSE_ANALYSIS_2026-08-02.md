## 二、根因分析

### 根因 1：实现驱动测试（Implementation-Driven Testing）

**现象**：E2E-SB-009 测试名为"折叠后图标列可见"，验证的是 `#sidebarIcons` 元素在折叠后可见——这恰好验证了**错误的实现**而非**用户需求**。

**根因链**：
```
实现先行 → 48px 图标列 → 测试按实现编写 → E2E-SB-009 验证图标可见 → 验收通过
                                                                    ↓
                                                            实际需求：完全隐藏
                                                            但无人质疑
```

**深层原因**：
- 测试编写者将"实现行为"等同于"正确行为"
- 缺少从用户视角出发的验收用例（"折叠后左侧不应有任何东西"）
- E2E-SB-001 测试断言 `sidebar-collapsed` 类存在，而非断言侧栏宽度为 0 或不可见

**影响范围**：`sidebar-behavior.spec.ts` 全部 11 个测试、`visual-regression.spec.ts` 快照基线

---

### 根因 2：Mock 驱动的测试盲区（Mock-Driven Blindness）

**现象**：`tauri-stub.js` 默认返回 `state.docs = []`（空文档列表），但**没有任何测试验证空库状态下的 UI 行为**。

**根因链**：
```
tauri-stub.js → state.docs = [] → loadDocuments() → docCount = 0 → 输入框应禁用
                                                                    ↓
                                                          但无测试断言此状态
                                                          测试直接进入聊天流程
```

**深层原因**：
- E2E 测试**全量使用 mock**，从不接触真实后端
- `chat.spec.ts` 的 11 个测试都假设文档已存在，直接测试聊天流程
- `helpers.mjs` 的 `enterApp()` 函数不注入任何文档
- Mock 返回空数组时，前端 UI 应有反应（禁用输入），但无人验证这个反应是否正确
- 这是一个典型的"假阴性"：测试通过了，但验证的场景不完整

**影响范围**：全部 50+ E2E spec 文件（都依赖 `tauri-stub.js`）

---

### 根因 3：空状态测试缺失（Missing Empty-State Coverage）

**现象**：没有任何 E2E 测试从"空知识库"状态出发，验证：
1. 输入框是否禁用
2. 发送按钮是否禁用
3. placeholder 文案是否正确
4. 导入文档后是否恢复可用

**根因链**：
```
测试设计聚焦"正常流程"（有文档→聊天→回答） → 空状态被视为"边界情况"而非"核心路径"
→ 无人编写空状态测试 → 输入框禁用逻辑从未实现 → 前端缺少防御性代码
```

**深层原因**：
- 测试设计方法论缺陷：只覆盖"正向路径"（happy path），不覆盖"前置条件不满足"路径
- 后端有 `count_documents() == 0 → error` 防御，但前端没有对应的 UX 防御
- 这是一个"前后端防御缺口"：后端拒绝，但前端不阻止，用户先输入再被拒绝

---

### 根因 4：无真实数据集成测试（No Real Data Integration Testing）

**现象**：`real-llm.spec.ts` 文件存在但需要 API Key + Base URL 环境变量，从未在 CI 中运行。没有任何测试：
1. 真实导入一个文件（如 `lisp-rs/README_zh.md`）
2. 等待嵌入完成
3. 输入文档中的相关字句
4. 验证回答包含文档内容

**根因链**：
```
E2E 全量 mock → 从不测试真实 RAG → 核心功能（检索+生成）零端到端验证
→ 但测试报告显示 "全部通过" → 产生虚假的信心
```

**深层原因**：
- 测试分层缺陷：单元测试 → 集成测试 → E2E（mock），缺少"集成 E2E（真实数据）"层
- `tauri-stub.js` 的 `chat` handler 返回固定 mock 文本，不经过 embedder/storage/LLM
- 真实 LLM 测试需要网络访问和 API Key，在 CI 中难以配置
- 嵌入模型首次下载需要 ~30MB + 数分钟，测试中不触发

## 三、系统性漏洞总结

| 漏洞编号 | 漏洞名称 | 影响 | 严重程度 |
|---------|---------|------|---------|
| V1 | 实现驱动测试 | 测试验证实现而非需求，错误实现也能通过 | 严重 |
| V2 | Mock 驱动盲区 | 全量 mock 导致真实后端行为零覆盖 | 严重 |
| V3 | 空状态覆盖缺失 | 前置条件不满足时的 UI 行为零验证 | 中等 |
| V4 | 前后端防御缺口 | 后端有防御但前端无对应 UX 防御 | 中等 |
| V5 | 无真实数据集成 | 核心功能（RAG Q&A）从未端到端验证 | 严重 |

## 四、改进方案

### 4.1 短期修复（已完成）

| 修复项 | 状态 | 验证方式 |
|-------|------|---------|
| 侧栏折叠完全隐藏 | ✅ 已完成 | `sidebar-behavior.spec.ts` 11 passed |
| 空库禁用聊天输入 | ✅ 已完成 | `sidebar-behavior.spec.ts` E2E-SB-010/011 |
| tauri-stub 图标列/浮层清理 | ✅ 已完成 | 源码已移除 `sidebarIcons`/`sidebarFlyout` |

### 4.2 中期改进（测试体系加固）

#### 4.2.1 用户视角验收用例模板

每个功能需求必须包含以下视角的测试：
```
- 正向路径：正常操作流程（已有文档→聊天→回答）
- 空状态路径：前置条件不满足时的 UI 行为（无文档→输入禁用→引导导入）
- 状态转换路径：从前置条件不满足到满足的转换（空→导入→可用）
- 错误恢复路径：后端错误时的前端恢复行为
```

#### 4.2.2 Mock 分层策略

```
单元测试 → 纯 mock（函数级隔离）
集成测试 → 真 storage + mock embedder（Rust 层）
E2E 测试 → tauri-stub（前端 UI 流程）
真实 E2E → 真实 Tauri + 真实文件 + 真实 embedder + mock LLM（可选）
```

#### 4.2.3 真实数据测试规范

新增 `real-data.spec.ts`（CI 中可选运行）：
```typescript
test('真实导入 lisp-rs README 并验证 RAG', async ({ page }) => {
  // 1. 使用真实 Tauri IPC 导入文件
  // 2. 等待嵌入完成（doc-status-changed → Indexed）
  // 3. 输入文档中的关键词（如 "Lisp 语法规则"）
  // 4. 验证回答包含文档内容（如 "两条规则"）
  // 5. 验证引用来源包含 lisp-rs README
});
```

### 4.3 长期改进（体系级）

#### 4.3.1 需求→测试可追溯性矩阵

每个 SRS 需求（REQ-XXX）必须关联至少一个验收测试用例，且测试用例必须从**用户视角**编写，而非从实现视角。

#### 4.3.2 前端防御性编程规范

对于所有依赖后端前置条件的操作（如"有文档才能聊天"），前端必须有对应的 UX 防御：
- 禁用输入控件
- 显示引导文案（placeholder/hint）
- 在 `send()` 中做前端层拦截（早返回 + toast 提示）

#### 4.3.3 测试设计评审制度

新增 E2E 测试时，必须回答：
1. 这个测试验证的是**用户需求**还是**当前实现**？
2. 如果实现改变（如 48px → 0px），测试是否需要修改？如果需要，说明测试耦合了实现。
3. 是否覆盖了空状态/前置条件不满足的路径？
