## 第零章 评估方法论

### 0.1 评估哲学

EchoMind 经历了 v1.0 → v1.20 共 20+ 个大版本迭代，累计 250 个 SRS REQ 全部完成、79 个前端模块、220/230 个 IPC 命令。项目在功能数量上已经非常丰富，但**功能数量 ≠ 产品质量**。

本次评估的核心准绳是：**使用越简单，功能越强大**。

这两个要求看似矛盾，实则互补：
- **简单**不是削减功能，而是让用户**不需要理解就能使用**
- **强大**不是堆砌功能，而是让每个功能都**真正解决用户问题**

### 0.2 评估维度

| 维度 | 权重 | 核心问题 |
|---|---|---|
| 用户旅程完整性 | 25% | 从首次打开到深度使用，每一步是否顺畅？ |
| UI 交互简洁度 | 25% | 界面是否过载？操作路径是否过长？设置是否过多？ |
| 功能真实价值 | 20% | 每个功能是否真正解决用户问题？是否有用户场景？ |
| 代码健康度 | 15% | 是否有僵尸代码？模块职责是否清晰？依赖是否合理？ |
| 架构合理性 | 15% | 是否过度设计？借鉴功能是否集成？抽象层次是否恰当？ |

### 0.3 评分体系

| 等级 | 含义 | 处置 |
|---|---|---|
| A | 优秀 — 超越期望 | 保持 |
| B | 良好 — 满足要求 | 小幅优化 |
| C | 需改进 — 有明显问题 | 中等改动 |
| D | 不合格 — 严重问题 | 大改 |
| F | 需重写 — 方向错误 | 推倒重来 |

### 0.4 评估方法

1. **逐模块审计**：每个 JS 模块、每个 IPC 命令、每个 Rust 模块逐一审查
2. **用户场景模拟**：从新用户到高级用户的完整旅程走查
3. **代码静态分析**：依赖关系、行数、导入链、调用链
4. **界面截图审查**：每个界面元素的必要性评估
5. **对比竞品**：与 ChatGPT / Claude / Obsidian / Notion 等对比交互复杂度

## 第一章 头脑风暴 —「使用越简单，功能越强大」标准定义

### 1.1 头脑风暴发散

#### 1.1.1 「使用越简单」的发散

**什么是简单？**

- 简单 = 用户不需要思考就能完成操作
- 简单 = 界面上只有当前任务需要的信息
- 简单 = 错误信息人类可读，并提供恢复建议
- 简单 = 相似操作在不同地方表现一致
- 简单 = 默认配置就是最佳配置
- 简单 = 高级功能按需展开，不干扰普通用户
- 简单 = 拖拽即可导入，不需要选格式
- 简单 = 输入框打字 Enter 即可提问，不需要配置检索参数
- 简单 = 设置面板不超过 3 屏滚动
- 简单 = 功能入口不超过 7 个（米勒定律 7±2）

**什么不是简单？**

- 30 个设置子区域 ❌
- 10+ 个独立功能面板 ❌
- 5 个输入区 toggle 开关 ❌
- 12 个性能优化开关 ❌
- 术语化设置项（Speculative RAG / Proposition / ColBERT / RAPTOR）❌
- 开发者工具混入用户设置（Trace / Budget / Durable / RAG Eval）❌

#### 1.1.2 「功能越强大」的发散

**什么是强大？**

- 强大 = RAG 检索准确、快速、全面
- 强大 = 知识图谱自动构建，可视化分析
- 强大 = Agent 多步推理真正解决问题
- 强大 = 安全加密保护敏感数据
- 强大 = 本地 LLM 隐私优先
- 强大 = 多知识库管理自然
- 强大 = 导出/分享便捷
- 强大 = 性能优化对用户透明（自动选择最佳策略）
- 强大 = 文档格式全覆盖
- 强大 = 可观测性帮助用户理解 RAG 质量

**什么不是强大？**

- 功能数量多但用户不知道怎么用 ❌
- 学术概念堆砌（Proposition / ColBERT / RAPTOR / Speculative RAG）❌
- 借鉴功能只有代码没有 UI ❌
- 默认关闭的高级功能（用户永远不会开）❌
- 开发者工具伪装成用户功能 ❌

#### 1.1.3 矛盾识别

| 矛盾 | 当前状态 | 理想状态 |
|---|---|---|
| 功能数量 vs 认知负荷 | 220 IPC / 79 模块 / 30 设置区 | 核心功能 ≤ 20 IPC / 设置 ≤ 8 区 |
| 高级功能 vs 可发现性 | 12 个性能开关默认关闭 | 自动选择最佳策略，0 手动开关 |
| 借鉴创新 vs 用户价值 | 40+ 借鉴 IPC 命令 | 每个借鉴功能都有明确用户场景 |
| 安全性 vs 使用便利 | SecurityPosture / ShadowScreen | 用户只需设密码，其余自动 |
| 可观测性 vs 用户理解 | Trace / Budget / Eval 面板 | 简化为「RAG 质量」单一指标 |

## 第十章 执行路线图

### 10.1 总体原则

1. **先审计后改动**：每个改动前先确认问题
2. **先删后改再加**：先清理僵尸，再优化现有，最后才考虑新功能
