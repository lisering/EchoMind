### 1.3 评分依据

#### .xlsx/.csv 文档导入（ROI 13.3）
- **用户需求度 4**：Excel 和 CSV 是企业用户最高频的数据格式。知识库用户经常需要导入表格数据（财务报表、研究数据、产品列表等）进行 RAG 查询。当前 13 种格式中缺少表格类格式，是明显的功能缺口。
- **技术可行性 5**：`calamine` crate 是纯 Rust Excel 读取库（支持 .xlsx/.xls/.ods/.xlsb），零 C 依赖，已在铁律九能力清单中列出。`csv` crate 是 Rust 标准级 CSV 库。两者均已成熟稳定。只需新增 `XlsxLoader` 和 `CsvLoader` 实现 `Loader` trait，扩展 `ALLOWED_EXTENSIONS`。
- **预计天数 1.5**：2 个 Loader 实现 + ALLOWED_EXTENSIONS 扩展 + 测试 + 文档。
- **互联网搜索引用**（铁律八）：
  - calamine crate: https://crates.io/crates/calamine （纯 Rust，MIT/Apache-2.0）
  - csv crate: https://crates.io/crates/csv （纯 Rust，MIT/Unlicense）
  - 参考 AnyLLM 表格导入: https://docs.anythingllm.com/

#### 对话全文搜索（ROI 13.3）
- **用户需求度 4**：用户积累大量对话后，查找历史讨论内容是高频需求。当前仅支持会话列表浏览，无法搜索对话内容。对话搜索是知识管理工具的标准功能（ChatGPT、Notion AI 均支持）。
- **技术可行性 5**：EchoMind 已有 SQLite FTS5 全文索引（用于 `keyword_search` BM25 检索）。只需扩展 `messages` 表添加 FTS5 虚拟表或新建 `messages_fts` 表，新增 `search_messages` IPC 命令。前端新增搜索栏组件。零新增依赖。
- **预计天数 1.5**：FTS5 表 + IPC 命令 + 前端搜索 UI + 测试 + 文档。
- **互联网搜索引用**（铁律八）：
  - SQLite FTS5 文档: https://www.sqlite.org/fts5.html
  - ChatGPT 搜索功能: https://help.openai.com/en/articles/6825453-chatgpt-release-notes
  - 参考 Notion AI 搜索: https://www.notion.so/help/search

#### Contextual Retrieval 上下文增强嵌入（ROI 8.0）
- **用户需求度 4**：检索质量是 RAG 系统的核心竞争力。Anthropic 2024 年发表的 Contextual Retrieval 论文证明，为每个 chunk 添加文档级上下文前缀再嵌入，可将检索失败率降低 49%（结合 BM25 后降低 67%）。这是铁律十标记 🔄 待实现的前沿技术。
- **技术可行性 4**：EchoMind 已有 `LLMProvider` trait（非流式调用）和 `ImportService` 导入管线。实现方式：导入时对每个 chunk 调用 LLM 生成 50-100 token 的文档上下文摘要，prepend 到 chunk content 后再嵌入。需要 `import.contextual_retrieval` 设置键控制（默认关闭，因导入时 LLM 调用有成本）。可选缓存上下文到 `chunks` 表新增 `context` 列。
- **预计天数 2**：上下文生成逻辑 + chunk context 列 + 嵌入管线集成 + 设置键 + 测试 + 文档。
- **互联网搜索引用**（铁律八）：
  - Anthropic Contextual Retrieval 原文: https://www.anthropic.com/news/contextual-retrieval
  - 论文核心结论：Contextual Retrieval 将检索失败率降低 49%（单独），结合 BM25 降低 67%，结合 reranking 降低 67%（综合）
  - 实现方式：Claude 为每个 chunk 生成 50-100 token 的文档上下文，prepend 到 chunk text

#### 文档标签系统（ROI 7.5）
- **用户需求度 3**：用户导入大量文档后，需要按主题/项目/类型分类管理。当前仅靠文件名和领域分类（16 域自动），缺乏用户自定义标签。标签系统是知识管理工具的标准功能（Obsidian tags、Notion labels、Logseq tags）。
- **技术可行性 5**：`Document` 结构体新增 `tags: Vec<String>` 字段。`documents` 表新增 `tags TEXT` 列（JSON 数组存储）。标签过滤用 SQL `LIKE` 或 JSON 函数。前端新增标签管理 UI（文档列表标签筛选 + 标签输入）。零新增依赖。
- **预计天数 2**：Document 模型扩展 + DB 迁移 + 标签过滤 IPC + 前端标签 UI + 测试 + 文档。
- **互联网搜索引用**（铁律八）：
  - Obsidian Tags: https://help.obsidian.md/Editing+and+formatting/Tags
  - Notion Labels: https://www.notion.so/help/properties
  - 参考 Logseq tags: https://docs.logseq.com/

#### commands.rs 模块化拆分（ROI 5.0）
- **用户需求度 2**：纯内部重构，用户无感知。但 v1.3 SOLID 评估明确指出 `commands.rs` 7706 行严重违反 SRP（铁律十四），是代码可维护性的最大威胁。随着功能迭代，该文件会越来越难以维护。
- **技术可行性 5**：Rust module 系统原生支持子模块。将 `commands.rs` 按功能域拆分为 `commands/chat.rs` / `commands/import.rs` / `commands/security.rs` / `commands/graph.rs` / `commands/local_llm.rs` / `commands/settings.rs` / `commands/document.rs` / `commands/mod.rs`。纯文件移动 + `pub use` 重导出，零功能变更，零新增依赖。
- **预计天数 2**：模块拆分 + import 路径修正 + 验证全部测试通过 + clippy/fmt。
- **战略价值**：铁律十四 SOLID 原则 SRP 违例修复，虽然 ROI 数值不高，但是必须执行的技术债务清理。

### 2.3 功能 3：Contextual Retrieval 上下文增强嵌入（REQ-RAG-041）

#### 用户场景

用户导入文档时，系统为每个 chunk 调用 LLM 生成 50-100 token 的文档上下文摘要，prepend 到 chunk content 后再嵌入。这样每个 chunk 的嵌入向量不仅包含 chunk 自身语义，还包含文档级上下文，显著提升检索准确率（Anthropic 实测降低 49% 检索失败率）。

#### 技术方案

**推荐方案**：导入时 LLM 上下文生成 + chunk context 列 + 嵌入管线集成

1. **chunk 模型扩展**：`Chunk` 结构体新增 `context: Option<String>` 字段
2. **数据库迁移**：`chunks` 表新增 `context TEXT` 列
3. **上下文生成**：`ImportService` 导入管线在分块后、嵌入前，对每个 chunk 调用 LLM 生成上下文
   - Prompt: `请用 50-100 字描述以下文本片段在整篇文档中的上下文背景：<document_summary>\n\n<chunk_text>`
   - 使用 `LLMProvider::chat_stream()` 非流式收集完整响应
   - 失败优雅降级（context 保持 None，不影响导入）
4. **嵌入增强**：嵌入时使用 `context + "\n\n" + chunk.content` 作为嵌入输入
5. **设置键**：`rag.contextual_retrieval`（bool，默认 false，因 LLM 调用有成本）
6. **重建索引**：新增 `rebuild_contextual_embeddings` IPC 命令（对已有 chunk 生成上下文并重新嵌入）

> **互联网搜索引用**（铁律八）：
> - Anthropic Contextual Retrieval: https://www.anthropic.com/news/contextual-retrieval
> - 核心结论：为每个 chunk 添加 50-100 token 文档上下文，检索失败率降低 49%
> - 结合 BM25：降低 67%
> - 结合 reranking：降低 67%（综合）
> - 实现成本：每 1000 chunks 约 $0.02-0.05 LLM 调用成本（用户 BYOK 承担）
> - EchoMind 已有 S55 文档摘要（`Document.summary`），可作为上下文生成的文档级摘要输入

#### 依赖

无新增依赖（复用 `LLMProvider` trait + `tokio::spawn` + 已有 `Document.summary`）。

### 2.5 功能 5：commands.rs 模块化拆分（REQ-ARCH-001）

#### 用户场景

纯内部重构，用户无感知。v1.3 SOLID 评估明确指出 `commands.rs` 7706 行严重违反 SRP（铁律十四），是代码可维护性的最大威胁。按功能域拆分为子模块，每个模块 ≤ 1500 行，提升代码可读性和可维护性。

#### 技术方案

**推荐方案**：按功能域拆分为 `commands/` 目录子模块

```
crates/tauri-app/src/commands/
├── mod.rs              — 模块声明 + pub use 重导出 + ALLOWED_EXTENSIONS
├── chat.rs             — 对话相关命令（chat / abort_chat / chat_inner 等）
├── import.rs           — 文档导入相关命令（import_files / get_documents 等）
├── document.rs         — 文档管理命令（delete_documents / get_document_summary 等）
├── security.rs         — 安全相关命令（encrypt_database / unlock_database 等）
├── graph.rs            — 知识图谱命令（get_graph_data / export_graph 等）
├── local_llm.rs        — 本地 LLM 命令（set_llm_mode / download_model 等）
├── settings.rs         — 设置相关命令（get_settings / save_settings 等）
├── agent.rs            — Agent/Coordinator 命令（set_agent_enabled 等）
├── performance.rs      — 性能优化命令（缓存/压缩/渐进式等）
├── sync.rs             — 文件同步命令（sync_folder / watch_folder 等）
└── misc.rs             — 杂项命令（导出/模板/Wiki链接/分支树等）
```

**拆分原则**：
1. 每个子模块按功能域聚合相关 IPC 命令
2. `pub use` 重导出所有 `#[tauri::command]` 函数，保持 `lib.rs` 的 `generate_handler!` 不变
3. `*_inner` 函数随对应命令移到子模块
4. 共享辅助函数（如 `mask_api_key` / `derive_title`）放在 `mod.rs` 或 `common.rs`
5. 零功能变更，零新增依赖

> **互联网搜索引用**（铁律八）：
> - Rust Module System: https://doc.rust-lang.org/reference/items/modules.html
> - Tauri command registration: https://v2.tauri.app/develop/calling-rust/
> - SOLID SRP in Rust: https://rust-unofficial.github.io/patterns/principles/single_responsibility.html

#### 依赖

#### 向后兼容性
