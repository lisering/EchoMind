## 3. Learned（学到的）

### 3.1 技术认知

#### 🔍 学到的知识
1. **嵌入模型选择**:
   - bge-m3（1024维）比all-MiniLM-L6-v2（384维）检索质量提升15%
   - 语义分块比固定token分块召回率高8%

2. **RAG优化策略**:
   - Contextual Retrieval（Anthropic论文）提升检索相关性20%
   - Late Chunking上下文感知嵌入减少信息损失
   - HyDE查询改写提升长尾查询效果

3. **前端性能**:
   - esbuild IIFE打包比手写MODULE_ORDER拓扑序更可靠
   - vendor懒加载启动体积从5.1MB降至632KB（-87.6%）
   - CSS变量三层架构（tokens→components→utilities）易于主题切换

4. **Rust异步安全**:
   - `tokio::task::spawn_blocking`包装同步IO（SQLite/文件操作）
   - `CancellationToken`实现流中断（保留部分内容）
   - `RwLock`替代`Mutex`读多写少场景

#### 🔍 发现的问题
1. **测试脆弱性**:
   - E2E视觉测试基线过期导致假失败
   - 时序敏感测试（流式渲染）在CI慢机器上不稳定
   - 解决方案: 标记为CI-unstable + 放宽断言

2. **文档漂移**:
   - IPC命令数文档162 vs 实际179
   - 设置键文档遗漏新增项
   - 解决方案: 每次session强制同步文档

3. **过度工程**:
   - 本地LLM推理（mistral.rs）最终删除（-16,776行）
   - 多Agent协调、DAG工作流等学术功能无用户场景
   - 教训: 先验证PMF再投资复杂功能

### 3.2 流程认知

#### 🔍 有效的实践
1. **原子计划（Atomic Plan）**:
   - 每功能拆解为独立Session（1-2天）
   - ROI评估筛选Top功能（评分=价值/成本）
   - 零新增依赖约束减少风险

2. **Session管理**:
   - CURRENT_STATE.md作为权威状态快照
   - LOG.md时间线记录所有会话
   - NEXT_SESSION_PROMPT.md实现会话交接

3. **验收评估（S1-S4）**:
   - S1: 前端模块审计（79模块）
   - S2: IPC命令审计（236命令）
   - S3: UI界面评估（10标准）
   - S4: 用户场景验证（15场景）

#### 🔍 需要改进的
1. **规划 vs 执行**:
   - 规划文档过多（ATOMIC_PLAN.md × 5版本）
   - 实际执行常偏离计划（功能增删）
   - 需要更灵活的规划机制

2. **测试稳定性**:
   - E2E flaky test影响发布信心
   - 视觉回归测试基线维护成本高
   - 需要更好的测试隔离和超时控制

## 4. Lacked（不足的）

### 4.1 准备工作

#### 🔴 产品市场验证（PMF）
**问题**: 
- 功能开发优先级基于ROI评分，缺乏用户反馈
- 14个Pro功能评估中，4个考虑下沉（无付费意愿证据）
- 持续收入模型（P0-4）未解决

**影响**: 
- 可能投入资源开发无人使用的功能
- 商业化路径不清晰

**改进**:
- 早期用户访谈（10-20目标用户）
- 功能使用埋点（哪些功能被频繁使用）
- A/B测试验证付费意愿

#### 🔴 性能基准数据
**问题**:
- 性能分析基于代码级推断，缺乏真实用户数据
- 冷启动时间、检索延迟、内存占用无量化基准
- 不同硬件配置下的性能差异未知

**影响**:
- 无法回答"比竞品快多少"
- 优化方向可能错误

**改进**:
- 集成性能监控（可选用户同意）
- 建立基准测试套件（标准化硬件）
- 公开性能对比（vs Notion AI/Obsidian Copilot）

### 4.2 工具/资源缺失

#### 🔴 用户反馈系统
**问题**:
- 无应用内反馈入口
- 无崩溃报告收集
- 无功能请求跟踪

**影响**:
- 用户问题无法及时发现
- 功能优先级缺乏数据支撑

**改进**:
- 集成Sentry（崩溃报告）
- 添加反馈按钮（直接发送到GitHub Issues）
- 用户行为分析（可选匿名）

#### 🔴 自动化发布流程
**问题**:
- `sync-to-github.sh`仅同步代码，不自动创建Release
- 多平台打包需手动触发CI
- 版本号升级需修改8个Cargo.toml + tauri.conf.json

**影响**:
- 发布流程耗时（30-60分钟）
- 容易遗漏文件（曾忘记更新CURRENT_STATE.md）

**改进**:
- 完整CI/CD流水线（tag → build → publish → GitHub Release）
- 版本号统一管理（workspace version）
- 自动化CHANGELOG生成

### 4.3 沟通/协作

#### 🟡 文档过载
**问题**:
- 文档数量过多（SRS + ADR + SESSION + SOFTWARE_ASSET + ...）
- 新会话需读取多个文件才能开始工作
- 文档更新滞后（IPC命令数漂移）

**影响**:
- AI Agent上下文窗口占用高
- 人类开发者难以快速上手

**改进**:
- 文档分层（核心/参考/归档）
- 自动化文档同步（代码变更 → 文档更新）
- 精简文档数量（合并重复内容）

#### 🟡 测试维护成本
**问题**:
- E2E测试187个pre-existing失败（视觉回归/时序敏感）
- 测试基线需定期更新（mermaid图表/代码高亮样式）
- 跨平台测试不一致（macOS不支持GUI测试）

**影响**:
- 发布前需人工判断哪些失败可忽略
- CI红灯可能被忽视（"那是pre-existing"）

**改进**:
- 分层测试策略（核心路径 vs 可选功能）
- 视觉测试使用稳定组件（避免第三方库更新）
- 测试标签系统（@smoke @regression @flaky）

## 5. Longed for（希望改进的）

### 5.1 如果重来，会有不同做法

#### 💡 更早验证PMF
**当前做法**: 
- 基于ROI评分开发功能（技术驱动）
- 先实现再找用户

**理想做法**:
- 阶段0: 用户访谈（2周）→ 验证问题存在
- 阶段1: MVP（1月）→ 核心功能验证
- 阶段2: 迭代（持续）→ 基于反馈优化

**收益**: 避免开发无用户需求的功能（如本地LLM推理）

#### 💡 更简单的架构起点
**当前做法**:
- 六边形架构 + 8个crate + 179个IPC命令
- 适合长期维护，但初期复杂度高

**理想做法**:
- 单crate起步（monolith）
- 验证PMF后拆分（modular monolith）
- 最后微服务化（如需要）

**收益**: 加速早期迭代，减少架构开销

#### 💡 测试金字塔更早建立
**当前做法**:
- 单元测试 + E2E测试为主
- 集成测试较少（40+文件）

**理想做法**:
- 测试金字塔: 单元(70%) + 集成(20%) + E2E(10%)
- 契约测试（前后端接口）
- 性能测试（基准回归）

**收益**: 更快的反馈循环，更低的维护成本

## 6. PDCA循环分析

## 8. 风险与问题分析

### 8.1 遇到的意外问题

#### 🔴 本地LLM功能失败
**问题**: 投资23个Session开发的本地LLM推理功能（mistral.rs + 自研量化内核）最终删除
**原因**: 
- 技术挑战超预期（GPU内存管理、量化精度损失）
- 用户需求验证不足（大部分用户使用云端LLM）
- 维护成本高（跨平台兼容性）

**应对**: 
- 大简化重构Phase 1 R3: 删除10个模块（-16,776行）
- 保留BYOK架构（用户自带API Key）

**教训**: 
- 先验证PMF再投资复杂功能
- 技术可行性 ≠ 商业可行性

#### 🔴 E2E测试脆弱性
**问题**: 187个pre-existing失败（视觉回归/时序敏感）
**原因**:
- 第三方库更新（mermaid/highlight.js）导致样式变化
- CI环境差异（慢机器时序超时）
- 测试设计不稳定（依赖CSS动画状态）

**应对**:
- 标记为CI-unstable（不阻塞发布）
- 定期更新视觉基线
- 放宽断言（容忍1-2px差异）

**教训**:
- E2E测试应覆盖核心路径，非全部功能
- 视觉测试使用稳定组件（避免第三方依赖）

#### 🟡 文档漂移
**问题**: IPC命令数文档162 vs 实际179
**原因**:
- 新增命令后忘记同步文档
- 多人协作（AI Agent）导致遗漏

**应对**:
- 每session强制同步文档
- CURRENT_STATE.md作为权威来源

**教训**:
- 文档应自动化生成（代码 → 文档）
- 减少文档数量（避免信息过载）

### 8.2 未被识别的风险

#### ⚠️ 商业模式风险
**问题**: 买断制 + 无订阅/云服务 = 持续收入模型缺失
**影响**: 
- 无法支持长期开发
- 用户获取成本高（无免费增值）

**缓解**:
- Pro功能差异化（多模态/自定义模型）
- 企业版授权（团队协作/管理后台）

#### ⚠️ 竞品风险
**问题**: Notion AI / Obsidian Copilot / Mem 持续迭代
**影响**: 
- 功能同质化
- 用户迁移成本低

**缓解**:
- 差异化: 本地优先 + 隐私保护 + Rust性能
- 聚焦: 知识图谱 + 专业领域（法律/医疗/科研）

#### ⚠️ 技术栈锁定风险
**问题**: Rust + Tauri v2生态相对小众
**影响**:
- 招聘困难（Rust开发者稀缺）
- 社区支持有限

**缓解**:
- 文档完善（AGENTS.md + PROJECT_RULES.md）
- AI Agent辅助开发（降低门槛）
- 关键模块抽象（可替换底层实现）


**改进**:
- 招募产品经理（用户研究）
