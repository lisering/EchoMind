# EchoMind（灵犀）系统约束（铁律规则）

> 本文件是 **EchoMind（灵犀）** 项目的绝对强制规则，每次新建对话都必须严格遵守，不可跳过、不可遗忘。
> 与 `PROJECT_RULES.md`、需求规格文档（`docs/SRS_v1.0.md`）、测试策略文档共同构成「唯一真相源」。
>
> **项目概要**：EchoMind 是一款基于 Rust + Tauri v2 的本地优先 AI 知识库桌面应用。
> 核心链路：文档导入 → 本地解析/分块/向量化 → BYOK 大模型 RAG 检索增强对话。
> 核心承诺：Rust 极速、隐私不出域、BYOK 买断制。
>
> **技术栈**：Rust (Edition 2024) + Tauri v2 + 六边形架构 + Vanilla JS (esbuild IIFE)
> **Crate 结构**：`models`（数据契约）→ `core`（业务逻辑/Trait）→ `infra`（适配器）→ `tauri-app`（IPC 外壳）+ `compact`（上下文压缩）+ `prompt`（提示词构建）+ `license-issuer`（许可证签发）
> **依赖方向铁律**：`tauri-app → core → models`，严禁反向依赖

## 铁律一：网络代理设置（仅限开发调研，软件本身禁止代理）

**⚠️ 核心原则：代理仅用于 AI Agent 的开发调研活动（搜索资料、下载依赖、抓取文档）。软件本身运行时（API 调用、模型下载、任何用户面向的网络请求）绝对禁止使用代理。**

### ✅ 允许使用代理的场景（开发调研活动）

当 AI Agent 进行以下开发活动遇到无法访问的资源时，可以使用代理：

```bash
export https_proxy=http://127.0.0.1:7890
export http_proxy=http://127.0.0.1:7890
export all_proxy=socks5://127.0.0.1:7890
```

- `cargo build` / `cargo update` 下载 crates 时
- `npm install` 下载依赖时
- 模型下载（**仅限开发环境**）
- `web_fetch` / `curl` 抓取外部文档时
- 技术选型调研（GitHub API / crates.io 搜索）
- 任何 AI Agent 执行的开发相关网络命令

### 🚫 禁止使用代理的场景（软件运行时）

**软件本身的网络请求绝对不能走代理。** 软件面向终端用户，用户不一定有代理环境，软件必须能在无代理环境下正常工作：

- **外部 API 调用**（如 LLM API 请求）：用户配置的端点必须直连
- **模型/资源下载**：用户下载模型或资源时直连
- **运行时首次加载的依赖下载**：用户使用软件时触发的下载直连
- **Web 搜索等功能**：用户使用网络功能时直连
- **任何其他用户面向的网络请求**

### 规则

1. **开发调研时**：如果命令可能涉及网络访问，默认在命令前加 `export https_proxy=http://127.0.0.1:7890 http_proxy=http://127.0.0.1:7890 all_proxy=socks5://127.0.0.1:7890 &&`
2. **首次执行网络命令失败时**（超时/连接拒绝），立即重试并加上代理
3. **代理地址固定为** `127.0.0.1:7890`，除非用户明确通知更改
4. **用完后必须立即 unset，防止代理泄露或影响其他任务：**
   ```bash
   unset https_proxy http_proxy all_proxy
   ```
5. **软件代码中绝对不能读取或使用代理环境变量**：HTTP 客户端构建时不设置 `.proxy()`，不读取 `https_proxy` / `http_proxy` 环境变量。如果 HTTP 库默认读取了环境变量，必须在代码中显式禁用：
   ```rust
   reqwest::Client::builder()
       .no_proxy() // 🚫 禁止代理，确保软件直连
       .build()
   ```

## 铁律二：TDD 驱动开发

1. **所有功能必须 TDD 驱动**：先写红灯测试，再写实现代码使其变绿，严禁「先实现后补测试」。
2. **用例必须有效且有意义**：禁止写永远通过的空断言（如 `assert!(true)`）；每个用例必须明确对应一条 AC（验收标准），断言聚焦行为而非实现细节。
3. **根据开发进度持续调整**：随着需求演进和代码重构，测试用例必须同步更新。废弃的用例及时删除，新增的分支及时覆盖。测试代码与生产代码同等重要，接受同等质量的 review。
4. **测试左移纪律**：QA 在开发写代码之前介入编写测试骨架，此时测试必须失败（红灯），失败原因必须是「未实现」而非「测试本身错误」。
5. **模糊测试（Fuzzing）**：安全关键代码（解析器、解码器、加密、文件处理）必须编写模糊测试。使用 `cargo-fuzz`（基于 libFuzzer）对外部输入处理路径进行模糊测试，发现未知边界崩溃。模糊测试用例纳入 CI 定期运行（非每次 PR，但至少每周）。
6. **属性测试（Property-Based Testing）**：核心算法和数据转换逻辑应使用属性测试（如 `proptest`），自动生成大量随机输入验证不变量，而非仅靠手写用例。

### 测试金字塔（比例 70:20:10）

| 类型 | 比例 | 说明 |
|------|------|------|
| **单元测试** | 70% | 测试单个函数/模块，无外部依赖，使用 Mock |
| **集成测试** | 20% | 测试模块间协作，允许有限外部依赖 |
| **E2E 测试** | 10% | 端到端流程，仅在关键路径使用 |

### 测试规范

- 每个公共函数必须有对应的单元测试
- **测试名称格式**: `test_被测函数_场景_期望结果`（例: `test_calculate_division_by_zero_returns_error`）
- **AAA 模式**: Arrange(准备) → Act(执行) → Assert(断言)
- 一个测试只验证一个概念，避免多个断言链
- 外部依赖(IO/网络/数据库)必须使用 Mock 或 Stub
- 使用 trait 抽象外部依赖，测试时使用 Mock 实现
- 使用 `#[cfg(test)] mod tests` 组织测试模块
- 使用 tempfile 创建临时文件，使用 tokio::test 测试异步代码

### 覆盖率要求（按代码类别）

| 代码类别 | 最低覆盖率 | 理由 |
|---------|-----------|------|
| 安全关键（认证/加密/权限） | 90% | 高风险高影响，必须严格验证 |
| 业务逻辑（计算/规则/状态机） | 85% | 核心价值，必须正确 |
| API / IPC 端点 | 80% | 面向用户，必须可靠 |
| 工具函数 | 95% | 高度复用，易于测试 |
| UI 组件 | 70% | 聚焦行为而非渲染细节 |

### 测试反模式（禁止）

- **测试间依赖**：每个测试必须独立，禁止依赖执行顺序
- **硬编码测试数据**：使用工厂函数生成测试数据，断言使用计算值而非魔法数字
- **测试实现细节**：测试行为（输入→输出），不测试内部状态或调用次数
- **测试中 sleep**：使用 `waitFor` / 事件驱动而非固定等待时间

### Vibe Coding 全自动化测试体系（AI Agent 专用）

> 来源：template-agenticide-vibecoding (⭐76) / vibe-coding-ai-rules (⭐86) / cargo-nextest / cargo-mutants / insta / cargo-llvm-cov / wiremock

**核心原则**：vibe coding 最大的痛点是 90% 的时间用于验证。通过分层自动化测试体系，让 AI 写代码后自动验证，人类只做审查。

#### 分层测试门禁

| 层级 | 触发时机 | 命令 | 耗时 | 说明 |
|------|---------|------|------|------|
| **L0 Pre-commit** | 每次保存 | `cargo fmt --check` + `cargo clippy -p <crate>` | 秒级 | 格式+lint 单 crate |
| **L1 Fast Unit** | 写完一个函数 | `cargo nextest run -p <crate>` | 秒级 | 进程隔离+并行 |
| **L2 Integration** | 功能完成 | `cargo nextest run --workspace` + `cargo llvm-cov` | 分钟级 | 全量+覆盖率门禁 |
| **L3 Quality Gate** | CI 定期 | `cargo mutants` + `cargo miri test` + `cargo fuzz` | 小时级 | 突变/UB/模糊 |
| **L4 E2E** | 发版前 | Playwright bridge + axe-core + Vitest | 分钟级 | 端到端+无障碍 |

#### AI Agent 行为规则

1. **文件级命令优先**：默认使用单文件/单 crate 命令（3s），禁止未经用户批准运行全量 build（5min+）。
2. **写代码后立即验证**：完成一个函数后立即运行 L0+L1（秒级反馈），功能完成时运行 L2。
3. **快照测试消除手写期望值**：结构化输出（JSON/Markdown/序列化）使用 `insta::assert_snapshot!` 自动生成参考快照，`cargo-insta review` 交互式审查变更，免去手写大量 `assert_eq!`。
4. **HTTP Mock 隔离外部依赖**：LLM API / OAuth / 第三方 API 使用 `wiremock` Mock 服务器，请求匹配+响应模板+spying，测试不依赖真实服务。
5. **突变测试验证测试质量**：`cargo mutants` 自动修改源码（`+`→`-`、`if`→`if !`）运行测试，找到测试盲区。覆盖率只告诉你代码被执行了，突变测试告诉你测试是否真正检查了行为。CI 定期运行（每周/发版前）。
6. **nextest 替代 cargo test**：`cargo nextest run` 提供（a）进程级隔离——每个测试独立进程，一个 panic 不影响其他；（b）自动重试 flaky 测试；（c）慢测试超时；（d）分片并行；（e）JUnit XML 输出。
7. **信任分级减少审查负担**：
   - **Security Critical**（认证/加密/权限）→ 人工审查 + SAST + 突变测试
   - **Algorithms**（计算/规则）→ 单元测试 + 性能基准 + 同行审查
   - **Business Logic**（业务规则）→ 集成测试 + 利益相关者审查
   - **Boilerplate**（模板/配置）→ 自动化测试 + 快速审查
8. **3 次失败规则**：连续 3 次同一测试失败，停止自修复并求助用户。

#### 测试工具链清单

| 工具 | 用途 | CI 时机 |
|------|------|--------|
| `cargo-nextest` | 下一代测试运行器（进程隔离+重试+分片+JUnit） | 每次 PR |

## 铁律三：代码注释规范

1. **Rust**：充分发挥 Rust 强大的文档注释系统。所有 `pub` 项必须有 `///` 文档注释，说明用途、参数、返回值、错误条件与约束。模块级 `//!` 注释说明模块职责与架构约束。复杂逻辑用行内 `//` 注释说明「为什么」而非「是什么」。`cargo doc` 生成的文档必须可读且自解释。
2. **前端 JavaScript**：所有函数必须有 JSDoc 注释（`/** ... */`），标注 `@param`、`@returns`、`@throws`。复杂状态机和事件流必须有注释说明状态迁移与数据流向。严禁「无注释魔法函数」。
3. **注释与代码同步**：修改代码时必须同步更新注释。过时注释比没有注释更危险。Code review 时注释与代码不一致视为 review 阻塞项。
4. **杜绝屎山**：每个函数单一职责，命名自解释。超过 50 行的函数必须拆分。重复代码必须抽取。任何「暂时这样写，以后再改」的代码必须在注释中标记 `// TODO(req-xxx): 说明` 并关联需求编号。

## 铁律四：真实数据测试

1. **测试必须覆盖真实世界语料**：禁止仅用 toy data（如 `b"hello"`）作为唯一测试输入。L2 及以上测试必须包含真实公开语料（GitHub README、论文 PDF 等）和极端边缘数据（混合编码、恶意 XSS、空文件、深套目录），确保系统在野蛮场景下不崩溃。
2. **混沌测试常态化**：每次大版本迭代必须执行混沌测试集，覆盖抗压、容错、安全、格式欺骗、海量并发等野蛮场景。混沌测试用例与功能测试同等重要，纳入 CI 门禁。
3. **真实外部服务联调测试**：需要真实 LLM 或其他外部 API 的集成测试通过环境变量注入凭据，严禁硬编码 API Key。
   - API Key → 环境变量注入
   - Base URL → 环境变量注入
   - Model → 环境变量注入
4. **语料生成自动化**：测试 fixtures 由脚本自动生成，确保可复现。网络获取失败时使用本地 fallback，保证 CI 离线可跑。

## 铁律五：生产级代码质量（零 unwrap / 零 panic / 零裸溢出）

1. **零 unwrap / 零 expect**：生产代码严禁出现 `.unwrap()`、`.expect()`、`panic!()`、`unreachable!()`、`todo!()`、`unimplemented!()`。所有可能失败的操作必须经 `?` 传播或 `match` 显式处理，错误类型用 `thiserror`（领域层）或 `anyhow`（组装层）定义。CI 以 deny lint 强制。
2. **零裸整数溢出**：涉及用户输入或外部数据的算术运算（文件大小、配额计数、分块偏移等）必须使用 `checked_*` / `saturating_*` 系列方法或显式范围校验，严禁依赖默认 wrapping 行为。
3. **零 unwrap 链式调用**：禁止 `.map(|x| x.unwrap())`、`if let Some(x) = opt.unwrap()` 等变体绕过 lint。`Option::unwrap` 与 `Result::unwrap` 一视同仁，均以 `ok_or` / `context` / `map_err` 替代。
4. **错误信息安全**：错误消息严禁包含 API Key、文件路径中的用户名、数据库连接串等敏感信息。`anyhow::Context` 的描述须聚焦「做了什么」而非「内部细节」。
5. **防御性编程**：对外部输入（文件内容、网络响应、框架参数）执行长度截断、类型校验与字符边界检查后再使用。`String::from_utf8` 失败时用 `from_utf8_lossy` 容错，不得 panic。
6. **CI 门禁自动化**：每次 PR 必须通过 `cargo clippy --all-targets -- -D warnings`（含上述全部 deny lint），任何违反铁律五的代码不得合入主干。新增 crate 时须在 `Cargo.toml` 继承 workspace lints（`[lints] workspace = true`）。鼓励在非关键模块启用 `clippy::pedantic` 级别以获得更严格的代码质量检查。
7. **静态安全分析（SAST）**：CI 流水线应集成静态安全分析工具（如 `cargo audit`、`cargo deny check`），检测已知漏洞和许可证合规问题。安全关键模块的变更必须经过安全审查。
8. **未定义行为检测（Miri）**：涉及 `unsafe` 代码的 crate 必须通过 `cargo miri test` 检测未定义行为（越界访问、use-after-free、无效未初始化数据、数据竞争、对齐违规）。`unsafe` 代码块必须有充分的安全论证注释。
9. **`#![forbid(unsafe_code)]`**：经过审计确认无需 `unsafe` 的 crate，应在 `lib.rs` / `main.rs` 顶部添加 `#![forbid(unsafe_code)]`，防止后续引入 unsafe 代码。新增 `unsafe` 代码块必须附带安全论证（safety proof），说明为何该 unsafe 操作是 sound 的。

### 安全与可靠性约束

| 约束 | 说明 |
|------|------|
| **输入验证** | 所有外部输入必须验证 (长度/格式/范围/类型) |
| **防御式编程** | 不信任任何外部数据，假设最坏情况 |
| **资源安全** | 使用 RAII 模式，确保资源正确释放 (Drop/scopeguard) |
| **并发安全** | 共享状态使用 Arc<Mutex<T>> 或 channels，避免 data race；严禁跨 `.await` 持有 `std::sync::Mutex` |
| **敏感数据处理** | 密码/密钥不硬编码，使用环境变量或密钥管理服务；凭据仅本地存储 |
| **最小权限原则** | 只请求必要的权限和资源 |

## 铁律六：最新版本依赖原则

**所有用到的技术和依赖必须使用最新稳定版本。** 面对新版本时，必须去官网查阅 API 文档和迁移指南，不能凭记忆假设 API 用法。

版本更新规则：

1. **每次开始新功能开发前**，运行 `cargo update --dry-run` 和 `npm outdated` 检查是否有新版本
2. **遇到 API 破坏性变更**时，必须查阅官方迁移指南（Migration Guide），不能凭旧记忆编写代码
3. **新增依赖**时，必须在 `crates.io` 或 `npm` 确认最新版本号，不能手动猜测版本
4. **构建失败**时，首先考虑是否是依赖版本过旧导致的不兼容
5. **技术选型**时，优先选择官方维护活跃、文档完善的最新方案

版本检查命令：

```bash
# Rust 依赖更新检查
cargo update --dry-run

# npm 依赖更新检查
npm outdated

# 查看当前 Cargo.toml 中各依赖版本
grep -A1 "\[dependencies\]" crates/*/Cargo.toml
```

5. [ ] 无 `unsafe` 代码，或 `unsafe` 已审计
6. [ ] 在 `Cargo.toml` 中记录用途注释

## 铁律七：文档实时同步（大模型开发友好度保障）

**代码变更必须同步更新文档，文档与代码的脱节是项目质量的最大威胁。**

同步规则：

| 代码变更类型 | 必须同步更新的文档 | 时限 |
|---|---|---|
| 新增/修改 IPC 命令 / API 接口 | 接口契约文档 | 同一 PR 内 |
| 新增/修改数据库表 | 数据库结构文档 | 同一 PR 内 |
| 新增/修改 trait 方法 / 接口定义 | 代码契约文档 | 同一 PR 内 |
| 新增/修改数据模型 | 代码契约文档 | 同一 PR 内 |
| 新增/修改应用状态字段 | 代码契约文档 | 同一 PR 内 |
| 新增前端文件 | 前端模块文档 | 同一 PR 内 |
| 新增配置键 / 设置项 | 设置参考文档 | 同一 PR 内 |
| 新增事件 / 消息类型 | 设置参考文档 | 同一 PR 内 |
| 功能实现/补齐 | 需求规格文档对应 REQ 状态 | 同一 PR 内 |
| 新增架构决策 | `docs/architecture/adr/` 新建 ADR | 同一 PR 内 |

检查清单（每次 PR 提交前）：

1. [ ] 是否新增了 API 接口？→ 更新接口契约文档
2. [ ] 是否修改了数据库结构？→ 更新数据库结构文档
3. [ ] 是否新增了 trait 方法或数据模型？→ 更新代码契约文档
4. [ ] 是否新增了前端文件？→ 更新前端模块文档
5. [ ] 是否新增了配置键或事件？→ 更新设置参考文档
6. [ ] 功能状态是否变化？→ 更新需求规格文档
7. [ ] 是否有重大架构决策？→ 新建 ADR

### 文档治理原则（借鉴 Living Docs）

1. **一个事实一个归属**：每个概念、决策或需求只存在于一个文件中。跨文件引用而非复制——重复的描述是漂移的温床。
2. **未索引即不存在**：每个文档必须从索引文件（如 `README.md` 或 `index.md`）可达。禁止孤立文件。
3. **追加而非重写历史**：决策和需求是追加式的。当内容变更时，标记旧记录为 superseded 并新建记录，禁止静默重写历史。
4. **文档先行**：在向外部系统（Issue Tracker / Wiki / README）发布前，先在仓库内创建文档。仓库文件是唯一真相源。

AI Agent 开发前必读文档优先级：

1. `PROJECT_RULES.md` — 找回纪律约束（最高优先级）
2. `.catpaw/rules/system-constraints.md` — 本文件（铁律规则）
3. 代码契约文档 — 了解接口签名和数据模型（**第一技术参考**）
4. 接口契约文档 — 确认 API 参数和返回值
5. 数据库结构文档 — 确认表名/列名
6. `AGENTS.md` — 架构速查和已知陷阱

## 铁律九：Rust 生态优先原则

**所有功能实现必须优先使用 Rust 原生生态（crates.io / GitHub Rust 项目），除非经过充分调研确认 Rust 生态无可用方案。**

### 核心原则

对于 Rust 项目，所有核心能力必须在 Rust 生态内闭环。引入非 Rust 依赖（Python 脚本、C 库、外部进程）需要经过严格论证。

### 决策流程

1. **需求出现** → 先在 crates.io / GitHub 搜索 Rust 实现
2. **找到候选** → 检查 stars、活跃度、最近更新、文档质量
3. **多方案对比** → 优先选择纯 Rust 实现（无 C 依赖），其次选择有 Rust binding 的成熟 C 库
4. **Rust 无方案** → 记录调研过程，方可考虑非 Rust 替代（如调用外部 CLI）
5. **新增依赖** → 在 `Cargo.toml` 中记录用途

## 铁律十一：GitHub 发布同步规则（双仓库工作流）

**⚠️ 绝对铁律：如果项目采用双仓库工作流（开发仓库 + GitHub 发布仓库），发布仓库只放推到 GitHub 的文件——任何和打包编译无关的文件都不要放到这里。开发在项目根目录进行，每次源代码修改后必须立即同步到发布仓库，否则 GitHub 上的代码就是过时的。**

### 工作流架构

```
项目根目录                              ← 开发工作区（含 docs/ tests/ 等开发资产）
  └── <发布仓库>/                       ← GitHub 发布仓库（仅含打包编译必需文件）
        └── git remote → github.com/xxx/项目名   ← 推送到 GitHub
```

- **开发**：在项目根目录正常编码、测试
- **发布**：发布仓库只包含打包编译必需的文件，不含开发资产
- **同步**：根目录源代码变更后，**必须立即**运行同步脚本

### 同步时机（强制）

以下场景必须在完成修改后**立即**执行同步：

1. 修改了任何源代码文件（`.rs` / `.html` / `.css` / `.js` / `.json` / `.toml` 等）后
2. 新增或删除了源文件后
3. 修改了配置文件（`Cargo.toml` / `Cargo.lock` / 框架配置等）后
4. 修改了前端资源文件后
5. **每次对话结束前**，如果有源代码变更，必须运行同步脚本

### 不同步的文件

`docs/`、`tests/`、`e2e-tests/`、`.catpaw/`、`.githooks/`、`PROJECT_RULES.md`、`.catpaw/rules/system-constraints.md` 等开发专属资产不同步。

## 铁律十二：Session 上下文全自动管理（保证开发连续性）

**⚠️ 绝对铁律：Session 上下文管理是 AI Agent 的自动行为，不需要人工介入。Agent 在每次会话开始时自动读取上下文，在每次会话结束时自动更新状态。`docs/sessions/` 是跨会话上下文管理的唯一权威目录。**

### Session 管理目录结构

```
docs/sessions/
├── README.md              ← 索引 + 使用指南
├── CURRENT_STATE.md       ← 当前项目状态快照（Agent 自动更新）
├── HANDOFF_TEMPLATE.md    ← 衔接提示词模板
├── LOG.md                 ← 会话时间线日志（Agent 自动追加）
└── archive/               ← 历史会话详情归档
```

### Agent 自动行为：会话开始时（强制）

1. **读取 `docs/sessions/CURRENT_STATE.md`** — 获取最新项目快照（测试数、已完成功能、待办任务、关键约束）
2. **浏览 `docs/sessions/LOG.md`** — 快速了解前序 session 时间线
3. **如有特定功能上下文需求** — 在 `docs/sessions/archive/` 中查找对应历史记录
4. **确认铁律规则** — 读取 `.catpaw/rules/system-constraints.md` 确认当前约束

**这是 Agent 的第一优先级行为，优先于任何开发任务。**

### Agent 自动行为：会话结束时（强制）

1. **更新 `docs/sessions/CURRENT_STATE.md`** — 刷新测试数、已完成/待办列表、关键变更
2. **追加 `docs/sessions/LOG.md`** — 在时间线末尾添加本次 session 摘要
3. **创建 `docs/sessions/archive/` 归档** — 大型功能开发或复盘分析时创建详细归档记录
4. **如有源代码变更** — 同步更新软件资产文档对应章节
5. **无条件生成下个 Session 提示词** — 无论本次是功能开发、复盘分析、测试增强还是文档维护，**每次会话结束时都必须生成下个 Session 的衔接提示词文件**（`docs/sessions/NEXT_SESSION_*.md`）。提示词内容须包含：项目概要、上 Session 摘要、测试基线、下 Session 任务、约束、后续路径、关键文件索引
6. **运行同步脚本** — 如有源代码变更（铁律十一）

**Agent 不得在未完成上述步骤的情况下结束会话。**

### 衔接提示词输出格式

**⚠️ 衔接提示词必须放在一个完整的 Markdown 代码块中输出，用户只需点击一次「复制」按钮即可获取完整内容。**

## 铁律十三：前端样式必须使用 Tailwind 工具类 + CSS 变量（禁止冗余自定义 CSS）

**⚠️ 如果项目集成了 Tailwind CSS，并在 `tailwind.config` 中定义了全部设计 Token，前端样式必须优先使用 Tailwind 工具类，不得编写可用 Tailwind 替代的自定义 CSS。**

### 样式编写规则

1. **优先使用 Tailwind 工具类**：在 JS 中创建 DOM 元素时，直接在 `className` 中写 Tailwind 工具类
2. **设计 Token 通过 Tailwind config 使用**：颜色用语义化类名（如 `bg-surface-2`、`text-text-primary`），不要硬编码十六进制色值或 `var()` 表达式
3. **CSS 变量作为 Token 单一来源**：CSS 变量文件中的 `:root` 变量是设计 Token 的单一来源，`tailwind.config` 映射这些变量
4. **仅以下场景允许自定义 CSS**：
   - `@keyframes` 动画定义
   - 伪类/伪元素选择器
   - 父状态选择器（Tailwind 的 `group:` 无法表达任意父类名）
   - `user-select`、`-webkit-` 前缀等浏览器特定属性
   - 第三方库样式覆盖
   - CSS 变量定义
5. **禁止在自定义 CSS 文件中编写 Tailwind 能替代的规则**

### 违规示例与修正

```javascript
// ❌ 违规：自定义 CSS 类 + CSS 文件中写样式
el.className = 'msg-edit-actions-below';
// ✅ 正确：直接用 Tailwind 工具类
el.className = 'flex gap-0 justify-end mt-0';

// ❌ 违规：硬编码颜色
el.className = 'bg-[#1C1C20] text-[#F8FAFC]';
// ✅ 正确：用 Tailwind config 中定义的 Token
el.className = 'bg-surface-2 text-text-primary';
```

## 铁律十四：SOLID 架构原则

**采用六边形架构（Hexagonal Architecture）或类似分层架构的项目，其核心思想与 SOLID 原则高度一致。所有新增代码必须自觉遵循 SOLID 五大原则。**

### SRP：单一职责原则

**一个类/模块/函数只应有一个变更原因。**

1. **Crate / 包划分**：每个模块有且只有一个职责（领域契约、业务逻辑、适配器、组装层等分离）
2. **文件级**：每个文件只负责一件事（如查询编排、检索、分块分别独立文件）
3. **函数级**：超过 50 行的函数必须拆分；每个函数只做一件事，命名自解释

### OCP：开闭原则

**对扩展开放，对修改封闭。新增功能应通过新增代码实现，而非修改已有代码。**

1. **Port-Trait 扩展模式**：核心层定义 Port trait，新增功能只需新增 trait 实现，不修改已有实现
2. **条件编译门控**：可选功能通过 `#[cfg(feature = "xxx")]` 条件编译实现 OCP —— 新功能通过新增模块实现，不修改已有代码路径
3. **前端模块化**：前端模块互不依赖，新增 UI 面板只需新增文件并在入口注册

### LSP：里氏替换原则

**子类型必须能完全替换其基类型而不破坏程序正确性。**

1. **Trait 实现**：所有 trait 实现者必须遵守 trait 契约（参数约束、返回值语义、错误条件）
2. **占位实现**：`NoXxx` 占位实现必须与真实实现行为一致（返回空/默认值），保证调用方无感知切换
3. **默认实现**：trait 方法有默认空操作实现时，覆写后行为必须与默认语义一致

### ISP：接口隔离原则

**客户端不应被迫依赖它不使用的方法。**

1. **Trait 细粒度拆分**：不定义一个巨大的 trait，而是按职责拆分为多个细粒度 trait
2. **可选能力分离**：不同能力使用不同 trait（如单向量嵌入与多向量嵌入分离）
3. **Pro/可选 trait 分离**：可选功能通过独立 trait 定义，通过条件编译隔离

### DIP：依赖倒置原则

**高层模块不应依赖低层模块，二者都应依赖抽象。**

1. **Port-Adapter 架构**：核心层定义 Port trait（抽象），适配器层实现 Adapter（具体），组装层注入具体实现。核心层永远不 import 适配器层或组装层
2. **依赖方向铁律**：`组装层 → 核心层 → 领域模型层`，严禁反向依赖
3. **泛型注入**：引擎通过泛型参数接收 trait 实现，而非硬编码具体类型
4. **`*_inner` 测试模式**：IPC/API 命令的 `*_inner` 函数接收状态引用而非框架状态包装器，允许集成测试注入 mock runtime

### SOLID 违例检查清单

1. [ ] **SRP**：是否有类/函数承担多个职责？→ 拆分
2. [ ] **OCP**：新增功能是否修改了已有代码？→ 改为新增实现
3. [ ] **LSP**：trait 实现是否遵守 trait 契约？→ 修正不一致行为
4. [ ] **ISP**：是否有 trait 过于臃肿？→ 拆分为细粒度 trait
5. [ ] **DIP**：核心层是否依赖了适配器层或具体实现？→ 通过 trait 抽象解耦

## 铁律十五：Spec-driven Development（规格驱动开发）

**⚠️ 先写规格，再写代码。任何功能实现之前，必须先在需求规格文档或原子规划文档中定义完整的规格（REQ + AC + TC），经确认后方可进入实现阶段。规格是开发的唯一依据，实现偏离规格时必须先更新规格。**

### 核心原则

规格驱动开发是 TDD（铁律二）的上游纪律。TDD 要求「先写测试再写代码」，但测试从何而来？Spec-driven development 回答这个问题：**测试从规格的验收标准（AC）派生**。

```
规格（REQ + AC）→ 测试用例（TC）→ 实现 → 验证
     ↑                                      |
     └────────── 偏离时回写规格 ──────────────┘
```

### 规格必须包含的要素

| 要素 | 说明 | 示例 |
|---|---|---|
| **REQ-ID** | 唯一标识符，格式 `REQ-<域>-<序号>` | `REQ-RAG-043` |
| **优先级** | P0（核心）/ P1（重要）/ P2（增强） | `P2` |
| **状态** | Draft → Implemented → Done / Deprecated | `Draft` |
| **依赖** | 前置 REQ-ID | `REQ-ARCH-000` |
| **描述** | 功能行为的精确叙述 | 一段文字 |
| **验收标准（AC）** | 可验证的断言，每条 AC 对应至少一个 TC | `AC-1: ...` |
| **契约** | 涉及的 trait 方法 / 数据模型 / API 命令 / 数据库表 | 契约清单 |
| **关联测试（TC）** | 验证各 AC 的测试 ID 列表 | `TC-BOUND-001~005` |

### 开发流程（强制顺序）

1. **需求分析**：理解需求背景，明确「为什么做」和「做什么」
2. **规格编写**（红灯前置）：在需求规格文档新增 REQ 条目，包含完整 AC + 契约 + TC 列表
3. **规格确认**：确认 AC 覆盖全部行为路径（正常 / 边界 / 错误），TC 与 AC 一一对应
4. **测试编写**（TDD 红灯）：根据 TC 编写测试代码，此时测试必须失败
5. **实现编码**（TDD 绿灯）：编写生产代码使测试通过
6. **规格回写**：实现过程中如有偏离，**必须先更新规格再继续实现**
7. **文档同步**（铁律七）：实现完成后同步更新规格状态 + 契约文档 + 接口文档等
8. **验证闭环**：运行全部测试 + clippy + fmt，确认 TC 全部通过且对应 AC

### 与 TDD（铁律二）的关系

| 维度 | 铁律二 TDD | 铁律十五 Spec-driven |
|---|---|---|
| 层次 | 代码级 | 需求级 |
| 产出 | 测试代码 | REQ + AC + TC 规格文档 |
| 顺序 | 测试 → 实现 | 规格 → 测试 → 实现 |
| 关系 | TDD 是 Spec-driven 的执行阶段 | Spec-driven 是 TDD 的上游纪律 |

**两者互补**：没有规格的 TDD 是「无方向地写测试」，没有 TDD 的 Spec-driven 是「有方向但不执行」。项目要求两者同时遵守。

## 铁律十六：AI 生成代码审查与验证（AI-Generated Code Verification）

**⚠️ 核心原则：AI 模型可以生成看似正确但有隐藏缺陷的代码。所有 AI 生成的代码视为不可信，必须经过人工审查和自动化验证后才能合入主干。**

> 来源：vibe-coding-ai-rules security-rules.md（"Trust Nothing, Verify Everything"）+ SoloDawn 三层质量门 + agent-best-practices

### 信任分级

```
低信任                                          高信任
├─────────────┼─────────────┼─────────────┼─────────────┤
安全关键        算法逻辑        业务逻辑        样板代码

<─── 需要更多审查                          需要较少审查 ───>
```

- **安全关键代码**（认证/加密/权限）：人工审查 + SAST + 渗透测试
- **算法密集代码**（排序/检索/分块）：单元测试 + 性能基准 + 同行评审
- **业务逻辑代码**：集成测试 + 需求方确认
- **样板代码**（CRUD/DTO）：自动化测试 + 快速审查

### 审查规则

1. **理解每行代码**：禁止盲目接受 AI 输出。Review AI 生成代码时，必须理解每行代码的含义和副作用。
2. **边界用例优先**：AI 模型频繁遗漏边界情况（空输入、超大输入、并发竞态、编码异常）。Review 时必须检查边界处理。
3. **安全模式验证**：AI 可能复制训练数据中的不安全模式。必须检查：SQL 注入、XSS、命令注入、路径遍历、硬编码密钥。
4. **依赖真实性验证**：AI 可能引用不存在的 crate/npm 包或虚构的 API。新增依赖必须在官方仓库验证存在性。
5. **幻觉检测**：AI 可能生成看似合理但完全不存在的函数签名、配置项或 API 端点。所有 API 调用必须对照官方文档验证。
6. **测试真实性检查**：AI 可能生成假测试（空断言、恒真断言、被 skip 的测试）。Review 时必须验证测试确实执行且断言有意义。

## 铁律十七：结构化日志与可观测性（Structured Logging & Observability）

**⚠️ 所有日志必须结构化、分级、可追踪。禁止在日志中泄露敏感信息。**

> 来源：vibe-coding-ai-rules logging-rules.md + autometrics-rs + OpenTelemetry Rust（Metrics-API/Logs-SDK 已 Stable）

### 日志规范

1. **结构化格式**：所有日志必须使用 JSON 格式（或结构化键值对），禁止自由文本字符串。每条日志必须机器可解析。
2. **日志分级**：每条日志必须有正确的严重级别：
   - `DEBUG`：详细诊断，生产环境禁用
   - `INFO`：正常操作事件
   - `WARN`：异常但非错误的状况
   - `ERROR`：影响单个操作的失败
   - `FATAL`：系统级失败，需要立即关注
3. **关联 ID**：跨服务/模块的日志必须携带关联 ID（correlation_id / request_id），实现端到端追踪链路。
4. **上下文充分**：每条日志必须携带足够的上下文信息（who / what / where / when），能在孤立查看时有意义。

### 禁止日志中出现的敏感信息

- 密码 / 密钥 / Token / JWT
- API Key（即使是部分）
- 政府证件号 / 信用卡号
- 完整邮箱地址（应脱敏，如 `j***@example.com`）
- 数据库连接串
- 文件路径中的用户名

### Rust 实现规范

- 使用 `tracing` crate（非 `log`），支持 span 追踪和结构化字段
- 关键路径使用 `#[tracing::instrument]` 自动注入函数参数为 span 属性
- 异步上下文使用 `tracing::Instrument` 传播 span
- 生产环境日志输出 JSON Lines 格式，支持日期轮转
- 运行时日志级别可动态调整

### 可观测性三支柱

| 支柱 | 工具 | 用途 |
|------|------|------|
| **日志** | tracing + JSON Lines | 事件记录与诊断 |
| **指标** | Prometheus / autometrics | 性能监控与告警 |
| **追踪** | OpenTelemetry / tracing spans | 请求链路与依赖分析 |

### 无障碍自动化测试（axe-core）

前端 UI 变更必须在 CI 中集成 `axe-core` 自动化无障碍测试，覆盖 WCAG 2.0/2.1/2.2 Level A/AA 规则。`axe-core` 零误报，可自动检测约 57% 的 WCAG 问题，剩余部分需人工审查。每次新增或修改 UI 组件时，必须运行 axe-core 扫描并修复全部 violations。

## 铁律十八：LLM 应用安全防护（LLM Application Security）

**⚠️ 集成 LLM 的应用必须防御提示注入、验证 LLM 输出、脱敏 PII 后再送入模型。LLM 是不可信的外部服务。**

> 来源：**OWASP GenAI LLM Top 10 2026**（2026-08-04 发布）+ llm-hackers-handbook + Doberman-Core

### 致命三要素（Lethal Trifecta）

> Simon Willison (2025)：一个 Agent 同时具备以下三项能力时，存在高影响 exploitation 风险——移除任意一项即可消除条件：

| 要素 | 说明 |
|------|------|
| **A. 访问不可信输入** | 用户输入、检索内容、工具输出、外部文档 |
| **B. 访问敏感数据** | 私有数据库、用户隐私、内部文档 |
| **C. 状态变更或外部通信** | 文件写入、Shell 执行、API 调用、发邮件 |

**Rule of Two（Meta AI 2025）**：[A,B,C] 三者同时存在的 Agent 需要每次操作人工审批；[A,B] 或 [A,C] 配置需要显式残余风险评估。NIST AI 100-2 E2025 和 CISA/FBI/NSA 联合指南均认可此原则。

### 提示注入防御（OWASP LLM01:2026）

1. **输入与系统提示隔离**：用户输入必须与系统提示明确分隔，禁止将用户输入直接拼接到系统提示中。LLM 在架构上不区分「指令」和「数据」，不存在参数化查询的等价物。
2. **输入净化**：对用户输入执行标记过滤，检测并拦截已知的提示注入模式（如 "ignore previous instructions"、"system:" 前缀、角色扮演攻击）。
3. **不可见字符清除**：在每个输入和渲染边界剥离 tag-block（U+E0000-E007F）、variation-selector（U+FE00-FE0F）、zero-width（U+200B/200C/200D/2060）字符。这些字符在正常渲染中不可见，可走私指令或渗出数据。
4. **输出验证**：不信任 LLM 返回的结构化数据（JSON / 代码 / 命令）。LLM 输出必须经过 schema 验证后才可使用。此为结构性验证，而非用第二个 LLM 调用验证。
5. **工具调用权限控制**：LLM 可调用的工具必须遵循最小权限原则。凭证和状态变更能力保存在应用代码中，而非模型中。每个工具声明其所需权限，运行时由确定性策略引擎校验。
6. **速率限制**：对 LLM API 调用实施速率限制，防止恶意用户通过大量请求消耗配额或触发 DoS。
7. **记忆写入视为特权操作**：Agent 记忆写入必须记录触发提示、分类是否包含指令内容、审批后方可跨会话持久化。
8. **自适应测试**：提示注入防御必须使用自适应攻击者（已知防御方案详情）进行红队测试。静态攻击成功率近零但自适应攻击成功率可超 90%。使用 AgentDojo / JailbreakBench 基准测试。

### 过度代理防护（OWASP LLM03:2026）

| 风险类型 | 说明 | 缓解措施 |
|---------|------|----------|
| **功能过剩** | 工具包含不需要的功能（如只需读取但授予了写入/删除） | 最小化工具功能，只实现必要操作 |
| **权限过剩** | 工具使用的身份拥有超出必要的权限 | 最小权限，按操作授予权限 |
| **自治过剩** | 高影响操作无需人工确认 | 人工审批（human-in-the-loop） |

**渐进式执行策略**：低后果/可逆操作自动审批；高后果/不可逆操作路由到人工审查：
- `audit`（记录）→ `warn`（警告）→ `block`（阻止）→ `escalate`（升级人工）

### PII 脱敏

- 用户输入在送入 LLM 前，必须经过 PII 检测和脱敏（替换为 `[REDACTED-TYPE]`）
- LLM 返回的内容在展示给用户前，必须检查是否包含其他用户的 PII（跨会话泄露）
- 审计日志记录 PII 检测事件（类型 / 数量 / 处理方式），不记录原始 PII 内容

### LLM 输出安全（OWASP LLM10:2026 Improper Output Handling）

- LLM 生成的代码片段在执行前必须经过沙箱隔离（超时 / 内存限制 / 网络隔离 / 临时目录隔离）
- LLM 生成的 URL / 文件路径必须验证合法性（防 SSRF / 路径遍历）
- LLM 生成的 SQL 必须使用参数化查询，禁止直接拼接执行
- LLM 输出在传递给下游系统前，必须在可信应用代码中进行结构性验证

## 铁律二十一：RAG 安全防护（向量与嵌入弱点）

**⚠️ 使用 RAG（检索增强生成）的应用必须防护向量嵌入层面的安全风险。嵌入层是应用信任边界的一部分。**

> 来源：**OWASP GenAI LLM Top 10 2026 LLM09: Vector and Embedding Weaknesses**（2026-08-04 发布）——这是 2026 版新增的独立类别，2025 版中不存在

### 核心威胁

| 威胁 | 说明 | 影响 |
|------|------|------|
| **嵌入逆转** | 存储的嵌入向量可被逆向恢复源文本。ZSInvert/Zero2Text 零样本方法可恢复 50-92% 的源文本 | 向量数据库泄露 = 源文档泄露 |
| **检索时数据投毒** | 攻击者向语料库注入内容，其嵌入靠近目标查询，被检索后污染 LLM 输出 | 仅 5 篇投毒文档可在百万级语料中达 90% 攻击成功率 |
| **检索干扰** | 攻击者插入「阻断器」文档，使 LLM 拒绝回答或声称无信息 | 可用性攻击，使 RAG 系统瘫痪 |
| **跨租户泄露** | 共享向量索引中，相似度搜索在全索引上运行，租户过滤在后应用层。可通过结果计数/分数分布/时序推断其他租户数据存在性 | 多租户场景下的信息泄露 |
| **语义缓存投毒** | 语义缓存使用余弦相似度阈值判断「相同」，攻击者可构造阈值附近的向量污染缓存 | 跨用户返回攻击者文本 |
| **多模态嵌入投毒** | CLIP/ColPali 等跨模态编码器将图片映射到文本向量空间。攻击者可构造图片其嵌入靠近敏感查询 | 图片检索为信任上下文 |
| **成员推断** | 攻击者通过提交部分文档/扰动查询分析响应，推断特定文档是否存在于索引中 | 隐私泄露 |

### 防护规则

1. **权限和访问控制**：租户范围过滤必须在索引查询内部执行，而非作为检索后过滤器。客户端提供的范围是建议而非控制。对高敏感度工作负载，使用物理隔离的索引。
2. **数据验证与来源追踪**：嵌入前标准化内容（剥离零宽字符、白色文本、Unicode 同形字）。为每个嵌入追踪来源（源/入库时间/信任级别/管道版本），使受污染批次可被撤销。
3. **信任级别隔离**：不同信任级别的内容（外部网页、内部机密文档、合作方数据）不得在共享索引中混合，除非有硬隔离。索引级隔离优于共享索引上的分类标签。
4. **异常检测**：在入库和检索时标记异常向量——新向量异常靠近大量常见查询（检索劫持特征）。监控查询返回过多高相似度匹配。不向客户端返回原始相似度分数。
5. **存储生命周期控制**：源文档删除时同步删除嵌入，并审计对账。向量数据库备份按源文档同等敏感级别处理。静止时加密嵌入，密钥与应用层分开管理。嵌入模型轮换时重新嵌入全部语料，禁止混合新旧向量。
6. **嵌入逆转防护**：向量数据库备份、发送到第三方服务的嵌入、错误配置的云存储暴露的嵌入，必须视为等同于源文档泄露。在 GDPR 等法规下，「仅嵌入泄露」不构成安全港。
7. **监控与事件响应**：保持不可变的检索活动日志（租户范围/查询/返回 ID/相似度分数）。监控租户过滤绕过尝试、跨租户检索异常、异常嵌入 API 消费。事件响应手册中「仅嵌入泄露」按源数据泄露处理。

## 铁律十九：错误处理与弹性设计（Error Handling & Resilience）

**⚠️ 区分操作错误与编程错误。所有外部依赖调用必须具备重试、熔断和优雅降级能力。禁止静默失败。**

> 来源：vibe-coding-ai-rules error-handling.md + Circuit Breaker 模式

### 错误分类

| 类型 | 说明 | 处理方式 |
|------|------|----------|
| **操作错误**（Operational） | 外部因素导致的可预期失败（网络超时、数据库锁定、文件不存在） | 重试 / 降级 / 传播给调用方 |
| **编程错误**（Programmer） | 代码缺陷导致的不可预期失败（TypeError / 逻辑错误 / 空指针） | 修复代码，不应 catch / 恢复 |

### 错误处理规则

1. **快速失败，显式失败**：在最早可能的点检测错误。输入在处理前验证，而非处理后报错。
2. **禁止静默失败**：空的 catch / `let _ = result` 是 bug，不是解决方案。每个被捕获的错误必须记录日志或传播。
3. **错误信息分层**：
   - **用户面**：脱敏的错误消息（不含堆栈/SQL/文件路径）
   - **内部**：包含完整上下文的详细错误（用于日志和调试）
4. **错误传播优先于嵌套匹配**：使用 `?` 操作符传播错误，避免深层嵌套的 `match`。使用 `anyhow::Context` 添加上下文。

### 弹性模式

#### 指数退避 + 抖动

```rust
// 重试外部依赖调用，指数退避 + 随机抖动
// base_delay * 2^attempt + random_jitter，上限 max_delay
```

#### 熔断器

- 连续失败超过阈值（如 5 次）→ 熔断器打开，快速拒绝请求
- 熔断器打开后经过冷却时间 → 进入半开状态，允许少量探测请求
- 探测成功 → 熔断器关闭，恢复正常流量
- 探测失败 → 熔断器重新打开

#### 优雅降级

- 外部依赖不可用时，系统应降级到可用的核心功能，而非整体崩溃
- 降级路径必须有测试覆盖
- 降级状态必须记录日志并通知用户

## 铁律二十：AI Agent 行为规范（AI Agent Behavioral Protocol）

**⚠️ AI Agent 在执行开发任务时必须遵循行为规范，确保可控、可追踪、可恢复。**

> 来源：agent-best-practices（15 Rules）+ vibe-coding-ai-rules best-practices.md

### 核心行为规则

1. **确认再执行**：复杂任务开始前，先复述理解确认无误后再动手。模糊的需求必须先提问澄清，禁止假设。
2. **快速失败**：连续失败 2-3 次同一操作，必须停止并升级/求助，禁止无限重试。
3. **时间盒**：单个问题最多尝试 3 次或 5 分钟，超时后必须求助或换方案。
4. **验证再推进**：每步操作完成后必须验证结果（编译通过 / 测试通过 / 文件存在），禁止假设操作成功。
5. **一次一件事**：完成当前任务并确认后，再开始下一个。禁止同时推进多个不相关任务。
6. **进度播报**：耗时超过 30 秒的操作，开始前说明即将做什么，完成后总结做了什么。禁止长时间沉默。

### 记忆持久化规则

- **写入文件，不做"脑内笔记"**：需要记住的信息必须写入文件，session 重启后 "脑内笔记" 会丢失。
- 重要发现 → 更新文档
- 学到的教训 → 更新规则文件
- 用户偏好 → 持久化到配置
- **文件 > 记忆**

### 安全行为规则

- **删除操作用 `trash` 而非 `rm`**：可恢复优先于永久删除
- **外部操作先确认**：发送邮件 / 发布消息 / 推送代码前，必须获得明确批准
- **不外泄私有数据**：禁止将项目内部数据发送到外部服务
- **遇到不确定时，询问**

### 代码注释规范

| 场景 | 规范 |
|------|------|
| 公共 API | 使用 `///` 文档注释，说明功能/参数/返回值/错误 |
| 复杂逻辑 | 使用 `//` 解释 **Why**(为什么) 而非 **What**(做什么) |
| 魔法数字 | 必须注释含义 (如 `// 30 seconds timeout`) |
| TODO/FIXME | 标记已知问题，格式 `// TODO(作者): 描述 - Issue #123` |

- 重大技术决策必须记录：问题/方案/权衡/决策/后果
- 存放在 `docs/architecture/adr/` 目录，命名格式：`ADR-NNN-简短描述.md`
