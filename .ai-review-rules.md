# EchoMind AI Code Review Rules

This document defines the AI code review rules for the EchoMind project.
The AI reviewer should follow these rules when analyzing pull requests.

## Security Rules

### S1: SQL Injection Prevention
- **Rule**: All database queries must use parameterized queries or prepared statements
- **Severity**: CRITICAL
- **Check**: Look for string concatenation in SQL queries, `format!()` in SQL, or raw SQL strings
- **Example**:
  ```rust
  // ❌ Bad
  let query = format!("SELECT * FROM users WHERE id = {}", user_id);
  
  // ✅ Good
  let query = "SELECT * FROM users WHERE id = ?1";
  conn.execute(query, params![user_id])?;
  ```

### S2: XSS Prevention
- **Rule**: User input must be sanitized before rendering in HTML
- **Severity**: CRITICAL
- **Check**: Look for unescaped user input in HTML templates or JavaScript string concatenation
- **Example**:
  ```javascript
  // ❌ Bad
  element.innerHTML = userInput;
  
  // ✅ Good
  element.textContent = userInput;
  // Or use DOMPurify for rich content
  element.innerHTML = DOMPurify.sanitize(userInput);
  ```

### S3: Command Injection Prevention
- **Rule**: Never execute shell commands with user-controlled input
- **Severity**: CRITICAL
- **Check**: Look for `Command::new()` with user input, `exec()`, `eval()` with strings
- **Example**:
  ```rust
  // ❌ Bad
  Command::new("sh").arg("-c").arg(user_input).output()?;
  
  // ✅ Good
  Command::new("specific_command").arg(safe_arg).output()?;
  ```

### S4: Path Traversal Prevention
- **Rule**: Validate file paths to prevent directory traversal attacks
- **Severity**: CRITICAL
- **Check**: Look for file operations with user-controlled paths without validation
- **Example**:
  ```rust
  // ❌ Bad
  let path = Path::new(user_input);
  
  // ✅ Good
  let base_dir = Path::new("/safe/directory");
  let path = base_dir.join(user_input);
  if !path.starts_with(base_dir) {
      return Err("Path traversal detected");
  }
  ```

### S5: Hardcoded Secrets
- **Rule**: Never hardcode API keys, passwords, or secrets in source code
- **Severity**: CRITICAL
- **Check**: Look for patterns like `api_key = "..."`, `password = "..."`, `secret = "..."`
- **Example**:
  ```rust
  // ❌ Bad
  const API_KEY: &str = "sk-1234567890";
  
  // ✅ Good
  let api_key = std::env::var("API_KEY").context("API_KEY not set")?;
  ```

## Performance Rules

### P1: N+1 Query Prevention
- **Rule**: Avoid querying inside loops; use batch operations instead
- **Severity**: HIGH
- **Check**: Look for database queries inside `for`, `while`, or `iter()` loops
- **Example**:
  ```rust
  // ❌ Bad
  for user_id in user_ids {
      let user = db.get_user(user_id)?;  // N queries
  }
  
  // ✅ Good
  let users = db.get_users_by_ids(&user_ids)?;  // 1 query
  ```

### P2: Blocking I/O in Async Context
- **Rule**: Never use blocking I/O in async functions; use `spawn_blocking` or async alternatives
- **Severity**: HIGH
- **Check**: Look for `std::fs::read`, `std::io::Read`, blocking network calls in async functions
- **Example**:
  ```rust
  // ❌ Bad
  async fn read_file(path: &str) -> Result<String> {
      std::fs::read_to_string(path)?  // Blocks the executor
  }
  
  // ✅ Good
  async fn read_file(path: &str) -> Result<String> {
      tokio::fs::read_to_string(path).await?
  }
  ```

### P3: Unnecessary Allocations
- **Rule**: Avoid unnecessary heap allocations in hot paths
- **Severity**: MEDIUM
- **Check**: Look for `Vec::new()` in loops, `String::from()` when `&str` suffices, unnecessary `.clone()`
- **Example**:
  ```rust
  // ❌ Bad
  for item in items {
      let s = String::from(item.name);  // Allocation per iteration
  }
  
  // ✅ Good
  for item in items {
      let s = &item.name;  // Borrow, no allocation
  }
  ```

## Architecture Rules

### A1: Hexagonal Architecture Compliance
- **Rule**: Core business logic must not depend on infrastructure or UI layers
- **Severity**: HIGH
- **Check**: Look for imports from `tauri`, `reqwest`, `rusqlite` in `crates/core`
- **Example**:
  ```rust
  // ❌ Bad (in crates/core)
  use tauri::State;
  use reqwest::Client;
  
  // ✅ Good (in crates/core)
  use crate::ports::{Storage, LLMProvider};
  ```

### A2: Dependency Direction
- **Rule**: Dependencies must flow inward: tauri-app → core → models
- **Severity**: HIGH
- **Check**: Look for reverse dependencies or circular imports
- **Example**:
  ```rust
  // ❌ Bad (in crates/core)
  use crate::tauri_app::AppState;
  
  // ✅ Good (in crates/tauri-app)
  use crate::core::AppState;
  ```

### A3: Trait-Based Abstractions
- **Rule**: Use traits for port definitions; never depend on concrete implementations
- **Severity**: MEDIUM
- **Check**: Look for concrete types in function signatures where traits would be appropriate
- **Example**:
  ```rust
  // ❌ Bad
  fn process(storage: &SqliteStorage) -> Result<()> { ... }
  
  // ✅ Good
  fn process(storage: &dyn Storage) -> Result<()> { ... }
  ```

## Rust Best Practices Rules

### R1: No unwrap/expect in Production Code
- **Rule**: Never use `.unwrap()` or `.expect()` in production code
- **Severity**: HIGH
- **Check**: Look for `.unwrap()`, `.expect()` outside of test modules
- **Example**:
  ```rust
  // ❌ Bad
  let value = some_option.unwrap();
  let value = some_result.expect("Failed");
  
  // ✅ Good
  let value = some_option.context("Missing value")?;
  let value = some_result.context("Operation failed")?;
  ```

### R2: Proper Error Handling
- **Rule**: Use `?` operator for error propagation; provide meaningful context
- **Severity**: HIGH
- **Check**: Look for `unwrap_or_else`, `match` with verbose error handling, silent failures
- **Example**:
  ```rust
  // ❌ Bad
  let value = match some_result {
      Ok(v) => v,
      Err(_) => return Ok(()),  // Silent failure
  };
  
  // ✅ Good
  let value = some_result.context("Failed to process")?;
  ```

### R3: Async Safety
- **Rule**: Never hold `std::sync::Mutex` across `.await` points
- **Severity**: HIGH
- **Check**: Look for `std::sync::Mutex` in async functions, especially with `.await` after lock
- **Example**:
  ```rust
  // ❌ Bad
  async fn process() {
      let lock = mutex.lock().unwrap();
      some_async_operation().await;  // Holds lock across await
  }
  
  // ✅ Good
  async fn process() {
      let value = {
          let lock = mutex.lock().unwrap();
          lock.clone()  // Copy data, release lock
      };
      some_async_operation(value).await;
  }
  ```

## Code Quality Rules

### Q1: Single Responsibility Principle
- **Rule**: Functions should do one thing; split complex functions
- **Severity**: MEDIUM
- **Check**: Look for functions longer than 50 lines, multiple responsibilities in one function
- **Example**:
  ```rust
  // ❌ Bad
  fn process_user_data() {
      // Validate input (10 lines)
      // Transform data (20 lines)
      // Save to database (15 lines)
      // Send notification (10 lines)
  }
  
  // ✅ Good
  fn validate_input() -> Result<()> { ... }
  fn transform_data() -> Result<()> { ... }
  fn save_to_database() -> Result<()> { ... }
  fn send_notification() -> Result<()> { ... }
  ```

### Q2: Documentation Requirements
- **Rule**: All public items must have documentation comments
- **Severity**: MEDIUM
- **Check**: Look for `pub` functions, structs, traits without `///` comments
- **Example**:
  ```rust
  // ❌ Bad
  pub fn calculate_similarity(a: &[f32], b: &[f32]) -> f32 { ... }
  
  // ✅ Good
  /// Calculate cosine similarity between two vectors.
  /// 
  /// # Arguments
  /// * `a` - First vector
  /// * `b` - Second vector (must be same length as `a`)
  /// 
  /// # Returns
  /// Similarity score between 0.0 and 1.0
  /// 
  /// # Panics
  /// Panics if vectors have different lengths.
  pub fn calculate_similarity(a: &[f32], b: &[f32]) -> f32 { ... }
  ```

### Q3: Test Coverage Requirements
- **Rule**: All public functions must have corresponding unit tests
- **Severity**: MEDIUM
- **Check**: Look for public functions without tests in `#[cfg(test)]` modules
- **Example**:
  ```rust
  // ❌ Bad
  pub fn process_data(input: &str) -> Result<String> { ... }
  // No tests
  
  // ✅ Good
  pub fn process_data(input: &str) -> Result<String> { ... }
  
  #[cfg(test)]
  mod tests {
      #[test]
      fn test_process_data_valid_input() { ... }
      
      #[test]
      fn test_process_data_empty_input() { ... }
  }
  ```

## Frontend Rules

### F1: DOM Manipulation Safety
- **Rule**: Sanitize user input before DOM insertion
- **Severity**: HIGH
- **Check**: Look for `innerHTML` with user input, `document.write()`, `eval()`
- **Example**:
  ```javascript
  // ❌ Bad
  element.innerHTML = userInput;
  eval(userCode);
  
  // ✅ Good
  element.textContent = userInput;
  // Use safe alternatives
  ```

### F2: Event Handler Memory Leaks
- **Rule**: Remove event listeners when components are destroyed
- **Severity**: MEDIUM
- **Check**: Look for `addEventListener` without corresponding `removeEventListener`
- **Example**:
  ```javascript
  // ❌ Bad
  function setup() {
      element.addEventListener('click', handler);
      // Never removed
  }
  
  // ✅ Good
  function setup() {
      element.addEventListener('click', handler);
      return () => element.removeEventListener('click', handler);
  }
  ```

### F3: State Management
- **Rule**: Avoid global mutable state; use unidirectional data flow
- **Severity**: MEDIUM
- **Check**: Look for global variables, direct DOM state manipulation
- **Example**:
  ```javascript
  // ❌ Bad
  let globalState = {};
  function updateState(key, value) {
      globalState[key] = value;
  }
  
  // ✅ Good
  const state = { /* initial state */ };
  function dispatch(action) {
      state = reducer(state, action);
      render(state);
  }
  ```

## Review Process

### When to Review
1. **Always review**: Security-related changes, authentication, encryption, database operations
2. **Always review**: Core business logic changes, architecture modifications
3. **Review on request**: Complex algorithms, performance-critical code
4. **Skip review**: Documentation-only changes, dependency updates (unless breaking)
